# 客户端更新与网络故障

本文沉淀 MaaHappyFish 使用 MFAAvalonia 原生更新链时的长期故障知识；Python Agent、Pipeline 与游戏自动化问题仍归对应功能文档。

## 2026-10-02 历史对话现场

以下来自删除前 Codex 会话中的本机日志/报告现场；报告与当时未提交工作树不在当前 Git 历史中，属于 **historical conversation evidence**，不能当作某个正式 commit 的实现事实。

### 更新资源半包假成功

历史报告 `更新资源半包假成功_20261002` 记录：15:48:16 下载响应体出现 TLS EOF，留下 131072000 字节、无 ZIP 中央目录/EOCD 的临时半包。日志随后出现“已下载更新包”和“更新资源完成”，但现场没有解压、覆盖或 Agent 重建证据，资源仍为 v0.7.3。

该现场能证明“网络下载失败 + 状态日志容易误导”，不能证明半包曾覆盖正式资源，也不能据此把根因归咎于代理、GitHub 或本机网络中的某一环。

### 自动检测更新 TLS 握手失败

历史报告 `自动检测更新TLS握手失败_20261002` 记录：17:08:54 SHA256 校验通过，17:09:14 完成安装；重启后的资源与日志确认已运行 v0.7.4。17:10:01 随后发生的是一次新的 GitHub Release 元数据查询 TLS 握手失败，并非又一次资源下载/覆盖；之后巡检完整运行正常。

因此“安装成功”和“后续版本查询失败”必须分开判断。旧文件清理阶段的 AccessDenied 告警后来消失，也不能单独用来判定一次更新是否成功。

## 2026-10-03 上游源码复核

2026-10-03 复核时，MaaXYZ/MFAAvalonia 最新正式版仍为 v2.16.2；该 tag 与上游当前 `MFAAvalonia/Helper/VersionChecker.cs` 的相关逻辑仍一致：

- `DownloadFileAsync` 捕获 `HttpRequestException`、`IOException` 等后返回 `(false, path)`；外层 `DownloadWithRetry` 主要等待抛出的 `WebException` 才进入下一轮。因此现场这类 EOF 失败会在内部被转换成 false，外层声明的多次重试并不能按预期覆盖它。
- 资源更新在下载前会设置/停止 MaaTasker；下载失败出口只结束本次更新状态，并不会恢复被停止的原任务。网络故障因此可能使挂机停在原游戏页面。
- “已下载更新包到临时文件”日志在检查 `downloadStatus` 之前输出；更新队列在 task action 正常 return 后还会记录“更新任务完成”。这两句只能说明执行走到该位置 / 函数返回，不能当成“下载成功”或“安装成功”的证据。
- 下载状态为 false 会在 SHA256、解压和正式覆盖之前返回；当前证据因此不支持“半包被安装”的说法。
- 已经是最新版时不会再次下载整包，但版本元数据查询本身仍可能遭遇网络/TLS 失败。

## MaaHappyFish 当前边界

当前 `.github/workflows/install.yml` 通过官方 Release 下载预编译 MFAAvalonia，`MFAA_VERSION` 为空时跟随最新正式版；`tools/install.py` 负责把预编译客户端与项目资源组合成发行目录，并不编译上述 C# 更新器源码。

因此，这类原生更新容错不能通过修改 MaaHappyFish 的 Python Agent 或 Pipeline 直接修复。可行方向是等待/推动上游修复，或明确维护并验证自有 MFAAvalonia 构建；在此之前不要把项目侧游戏逻辑补丁误写成“更新器已修复”。

## 安全处理与未来修复方向

这些是基于现场和源码得到的工程方向，不是当前已经实现的功能：

1. 对明确可重试的网络错误做有界重试，并让内部下载失败能真正到达重试层；
2. 使用临时 `.part` 文件，完成长度、摘要与 ZIP 完整性检查后再进入安装；
3. 尽量把停止 MaaTasker 推迟到完整包已经验证、即将覆盖安装的阶段；
4. 状态日志至少区分“检查失败 / 下载失败 / 无需更新 / 安装成功”，不要用“任务完成”代替业务成功；
5. 更新失败后不要自动重复会消耗游戏资源的业务任务。恢复前应由调用方确认页面和运行状态。

若改用 MFAAvalonia 的本地包入口，历史源码显示该入口存在，但本次对话没有做实际安装验证；本地包也不应拿现场半包直接尝试，使用前需自行核对完整包摘要和 ZIP 完整性。

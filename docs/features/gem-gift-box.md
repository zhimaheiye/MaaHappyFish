# 宝石礼盒兑换功能 (`GemGiftBoxTask`)

## 功能目标

从主鱼缸右下角宝箱进入宝石礼盒兑换页，依次处理 16、21、26、31、36、41、46 级七张配方卡片。每张卡片本日最多兑换至 `10/10`，完成后返回主鱼缸。

本功能使用用户提供的截图、模板和 ROI 实现；本轮仅做代码级验证，不代表 MFA 实机识别已经通过。

## 启动与导航契约

```text
GemGiftBoxTask
  ├─ 已在兑换列表 -> GemGiftBoxRun
  ├─ 已打开宝箱菜单 -> 识别点击宝石礼盒兑换入口 -> GemGiftBoxRun
  ├─ 主鱼缸 -> 识别点击右下角宝箱 -> 识别点击兑换入口 -> GemGiftBoxRun
  └─ 已停在兑换弹窗 -> 不点击兑换，跳过本子任务并尽量回到主鱼缸
```

- 右下角宝箱：`右下角_宝箱.png`，ROI `[1120,562,141,141]`。
- 兑换入口：`宝石礼盒兑换入口.png`，ROI `[828,575,132,121]`。
- 兑换列表页面门禁：OCR 稳定子串 `兑换鱼配方数`，兼容实机完整文本 `宝石兑换鱼配方数：21`。
- 进入列表后先检查 `16级配方`，基准 ROI `[55,196,108,41]`；未命中时只在列表页面门禁仍成立的前提下向页面顶部回滚，直到确认首屏。

## 七配方防重与防漏规则

固定处理顺序为：

```text
16 -> 21 -> 26 -> 31 -> 36 -> 41 -> 46
```

每一项都先 OCR 定位配方等级，再在同一张卡片内检查状态：

1. 识别到 `今日已兑换10/10`：该配方已经完成，跳过，不点击仍可能存在的 OK。
2. 尚未达到 `10/10` 且识别到同卡片 OK：按配方所在左右列和纵向位置推导同卡片 OK 搜索区，匹配 `宝石礼盒_可兑换.png`；OK 只作为可兑换状态门禁，不直接点击，进入单卡兑换流程。
3. 尚未达到 `10/10` 且连续复验无 OK：视为当前不可兑换（如宝石材料不足），记录为不可兑换项后跳过此配方，继续下一等级，不阻断后续其他配方。
4. 完成兑换、确认并返回列表后，复核配方状态：识别到 `今日已兑换10/10` 才记为完全兑换；否则按部分兑换结果继续下一配方，不重复提交。当前代码没有读取精确的 `1~9/10` 数量，也不能据此断定材料不足；“部分兑换”是流程收口状态，不是精确数量验收。

用户提供的基准映射为：配方文字 ROI `[55,196,108,41]` 对应同卡片 OK ROI `[587,195,47,35]`。两个矩形中心分别为 `(109,216.5)` 和 `(610.5,212.5)`，卡片点击点取二者中点并按常规四舍五入为 `(360,215)`。运行时使用实际识别框动态计算同一卡片的中点，横向仍锁定卡片右上角（右列放宽至 `[1180, ..., 80, ...]`），纵向根据当前 OCR 配方位置小范围跟随，以兼容列表滚动错位。

## 单卡兑换流程

```text
配方未满 10/10 且有 OK
  -> 识别同卡片 OK
  -> 点击配方文字与 OK 的中点（卡片主体）
  -> 模板确认兑换弹窗
  -> 模板识别加号并点击 9 次（材料不足时数量在可增加上限处停止）
  -> OCR 精确识别并点击“兑换”（兼容“兑换”与“兌換”）
  -> OCR 精确识别并点击“确定”
  -> 返回列表并复核：满 10/10 记为完全兑换，未满 10/10 记为部分兑换，均继续下一配方
```

- 兑换弹窗：`宝石礼盒_兑换识别.png`，ROI `[771,229,200,180]`。
- 加号：`宝石礼盒兑换_点击.png`，ROI `[878,336,134,132]`；识别一次后固定点击 9 次，每次间隔约 0.22 秒。该间隔是历史现场采用的兼容参数，不是已测定的固定动画周期，也不保证每次触摸都被游戏接受；不执行其他坐标兜底。
- 兑换按钮：OCR `^[兑兌][换換]$`，ROI `[789,486,169,131]`，严格避免误点“今日已兑换”计数文字。
- 确定按钮：OCR `^确定$`，ROI `[557,568,178,135]`。

## 结束契约与日常收尾集成

七个等级均完成本轮检查（可兑换项尽量兑换，已满项跳过，不可兑换项记录后跳过）后，OCR 点击左上角通用返回；在 `GemGiftBoxVerifyTank` 节点中通过 `主界面特征.png` 确认回到主鱼缸。

### 双出口路由契约 (Dual-Exit Routing)
为兼顾独立运行与日常收尾总控调用，`GemGiftBoxVerifyTank` 采用标准化双出口分流：
1. 触发 `GemGiftBoxDoneAction`：若日常收尾处于激活状态，安全推进日常收尾步骤并将 `GemGiftBox` 状态标记为 `DONE`；
2. 随后通过双出口分流：
   - `DailyRoutineReturnIfActive`：在 `daily_routine_state["active"] == True` 时流转回 `DailyRoutineDispatcher`；若已勾选宝石订单则继续 `GemOrderTask`，否则按队列进入下一项；
   - `DailyRoutineStandaloneDone`：在独立运行（`active == False`）时直接作为叶子节点正常成功退出（`ret=true`），绝不硬编码跌入未激活的 Dispatcher 引起超时判负。

### 日常收尾集成说明
- **运行顺序**：`FISHING` $\rightarrow$ **`GEM_GIFT_BOX`** $\rightarrow$ `GEM_ORDER` $\rightarrow$ `ROMANTIC_HOUSE`（只执行实际勾选项）；
- **默认勾选状态**：默认**不勾选**（不进入 `interface.json` 的 `default_case`），需由用户在 UI 的日常收尾任务选项中主动勾选启用；
- **独立任务保留**：`interface.json` 中完整保留 `GemGiftBoxTask` 独立入口，支持单独勾选运行与调试。

### 入口超时不再拖垮多鱼缸巡检（2026-10-05）

12:05:53 钓鱼因体力耗尽回到主鱼缸，12:05:55 日常收尾打印「开始执行：宝石礼盒兑换。」之后约 21 秒没有业务日志，12:06:16「任务失败：多鱼缸巡检」。值守签名写成幸运时刻挂起；同一时段框架日志被截断，17 分钟后的截图已是主鱼缸且没有弹窗。与日志对齐的是 `GemGiftBoxTask` 在默认约 20 秒内没有命中宝箱、入口或兑换列表，父节点又没有 `on_error`，`NextList.Failed` 把外层巡检判失败。当时的 `GemGiftBoxAbort` 是 `StopTask`，若真的走进去，任务更常显示成功而不是这次的 `FAILED`，所以失败发生在进入中止节点之前。

`GemGiftBoxTask` 现在等待 10 秒。入口、兑换弹窗、打开宝箱、兑换动作、返回和主鱼缸确认超时，都进入 `GemGiftBoxSkipAction`。日志写明已跳过本次兑换，并且不因此失败多鱼缸巡检。只有日常收尾仍停在 `GEM_GIFT_BOX` 时才把状态写成 `SKIPPED` 并推进一次，避免和成功回缸的 `DONE` 重复推进。恢复时先认 `主界面特征.png`；认不到才在左上角 OCR「返回」并点击，最多 4 次；仍然认不到就不点固定坐标，直接把日常队列交回调度器。独立运行的礼盒任务在这条恢复路径上用 `FailTaskAction` 报告失败。未知兑换弹窗不点击兑换按钮。

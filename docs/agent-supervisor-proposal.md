# 外部 LLM Agent 托管与自维护（长期设计草案）

**归档日期：2026-10-27。状态：已讨论的未来方向（proposed），未实现、未做 MCP 联调或实机验收。**

本设计用于保留后续开发时不能丢失的产品边界和分层原因；不是立即立项、授权自动改代码或改变现有发版优先级。技术现状须始终回当前 main、PROJECT_STATUS.md、docs/handoff/CURRENT.md、对应功能档案重新核验。本文归档时参考 main HEAD cc06523049cd02ca78122d43f3fc481c37a8cfd4。

## 一、定位：独立产品先行，Agent 是可选的上层

- **MaaHappyFish 本体继续作为无 AI 依赖的确定性视觉自动化工具**：面向普通使用者，继续拓展并充分实测日常、巡检、拼图、活动等功能。公开版不要求用户提供 LLM API Key。
- **可选外部 LLM Agent / MCP Adapter** 负责目标和策略、跨任务调度、异常接管、把经验转成候选代码/视觉资产；MaaFramework、现有 Pipeline、Python CustomAction/CustomRecognition 是执行与识别层。
- MaaFramework 的 Python AgentServer 与会推理的 LLM Agent 不是一回事。不要以“已有 agent/ 目录”为理由声称已接入智能决策。
- **不为接 AI 重写稳定 Pipeline**。Agent 通过稳定的任务/能力入口调用，不能依赖内部节点拓扑；插件可复用 MaaMCP 或框架 Python API，但具体适配方式须先验证对应版本。
- 限时活动的首轮探索、证据与临时脚本优先留在 happyfishagent；长期稳定且值得维护的确定性能力再下沉 MaaHappyFish。参照已有 docs/features/activity-takeover.md，不能将已注册的接管包误写成正式任务已接线。

## 二、当前已具备的基础与事实边界

- **收鱼产物**具有独立入口和长驻主循环，用户报告过单项约八小时持续运行；PROJECT_STATUS.md 亦有八小时观测记录。不能据此宣称所有模块（尤其多鱼缸巡检）均已达到整夜无人值守。
- 单/双缸收鱼已内嵌到点日常与好友摸宝等机制，已有按自然日去重及子任务返回主循环的实现，详见 docs/features/collect-fish.md 和 daily-routine.md。**未来的外部 00:00 / 12:00 高层调度是扩展设想，不是从零补现有十二点功能；不能与既有内部到点机制重复触发。**
- 每日魔幻拼图 **已有** 4×4、5×5、6×6 规格的 Solver/Executor；4×4 有实机成功记录，5×5/6×6 的部分路径仍处于 Candidate Ready 或待实机验收，见 docs/features/daily-magic-puzzle.md。此前聊天中的“拼图算法尚未研究完”只代表较早阶段，不是本次 HEAD 的当前状态。
- 项目已有业务状态容器、StartRouter/恢复路由、独立任务与日常嵌套的双出口、显式失败机制和故障取证体系；但这些**不等于**通用外部 Agent 能力注册、统一运行状态 API 或双向 MCP 调度已经完成。

## 三、未来能力契约（提案，不是已存在的接口）

对外暴露**业务能力**而不是任意内部 Pipeline 节点。建议先盘点已有 assets/interface.json 的任务 entry、选项及 docs 中 Start Contract，再逐步补机器可读的稳定语义；避免把同一参数定义在 UI 和新 registry 两份、造成漂移。

能力至少说明：

| 字段 | 含义 |
| --- | --- |
| 稳定标识、入口与参数 | 例如 collect_fish 映射现有 CollectFishTask；明确参数含义与默认来源 |
| 类型 | service（持续运行，如收鱼）或 job（会自然结束，如独立钓鱼） |
| 起始/恢复条件 | 支持哪些已知 UI 状态、必须先验证什么、哪些未知状态安全失败 |
| 完成与资源副作用 | job 的真实终态、service 的存活状态；金币/体力/免费次数等消耗和禁止事项 |
| 中止契约 | 何时能请求停止、如何确认真正停止、结束后页面和设备归属是否已确认 |
| 观测与证据 | 当前阶段、最后有效业务进展、真实错误码、截图/日志/节点追踪的可定位引用 |

建议的最小外部协议：list_capabilities、start_skill、get_skill_status、stop_skill，以及完成/失败/需要接管的事件订阅。可用状态至少区分 RUNNING、SUCCEEDED、FAILED、STOPPED；可再附 phase、run_id、reason、last_progress_at。**调用方发出停止请求≠已经停止；Maa 的 StopTask/成功色日志也不必然代表业务完成**，必须以真实终点、任务事件及必要的页面验证判断。

第一阶段可先做**只读状态/事件观测**，不改变正在稳定运行的收鱼点击逻辑。未来如输出 JSON 快照/JSONL 事件，应避免只解析中文 stdout 得出“健康”；明确进程启动时间、run_id、数据新鲜度、任务实际进展，避免把心跳、截图循环或原生层卡死误判为业务成功。建议由能够拿到真实 Tasker 生命周期事件的一层与已有 Python 业务状态共同生成，写入采用原子替换、过期判定，禁止多个实例互相覆盖。

## 四、调度与安全边界

目标场景：用户设置 00:00 / 12:00 两个刷新窗口；某项任务可能运行约一小时。外部 Agent 在合适时间协调当前长驻收鱼服务与一次性任务，确认真实完成/安全失败后再恢复挂机；若有多个任务，按有效期、用户优先级、资源条件和当前界面选择。**12:00 只是示意需求；刷新规则与奖励次数要依对应活动现场取证**，不能硬编码为全局事实。

- **互斥设备控制**：同一个 MuMu/ADB/Maa Controller 上，MFA、MaaMCP 与外部 Agent 不得各自并发盲点。须有执行权/租约、任务取消确认与安全交接点；既有长驻任务不应被另一个进程粗暴打断后默认可原路续跑。
- **调度幂等**：区分“本时段已尝试”“业务已完成”“失败/人工停止”，持久化执行记录；跨进程重启、跨自然日、手动已完成与已有内部日程的去重必须一起设计。不要因上一轮失败就无条件重试耗体力、购买或兑换。
- **风险分级**：账号付费/充值仍绝对禁止；未知消费弹窗、不可逆选择和未授权资源支出必须停止或等待用户预先定义的明确规则。未知页面没有可靠视觉门禁时不允许猜坐标。
- **异常接管**：Agent 应优先读真实失败原因、最新屏幕、动作轨迹与当前任务状态；若属于模拟器/客户端/ADB 底层故障，不得宣称修复了业务 Pipeline。
- 已成熟的 Maa 内部调度可继续原样工作；**外部 Agent 负责跨能力、跨时段、依事件决策**，不机械替换当前 DailyRoutine/CollectFish 的原有调度器。

## 五、经验反向维护项目（未来的自我改进闭环）

理想流程：现场识别失败或新活动 → 保存带来源和时间的截图/识别/动作前后帧/日志 → LLM 判断并临时处理 **安全且已授权** 的步骤 → 多次验证是否稳定 → 生成候选模板、ROI、Pipeline 片段或 Python 逻辑 → 代码级校验/模拟器专项验证 → 通过 review/PR 合入稳定版 → 将可重复环节交还 Maa，减少逐帧 LLM 消耗。

- 不把“成功点过一次”视作可靠自动化；将**原始证据、待验证经验、候选实现、已实机验证实现**分开管理。
- 能确定性识别的点击由 MaaFramework 执行；优先暴露单次识别、识别后立即动作以及已有命名 Pipeline，而非让 LLM 每次看图猜坐标。要防截图/识别结果过期导致点击错位。
- 代码生成与自维护 **不等于授权无人审查直接修改生产 main、热覆盖运行中的脚本或自行消耗游戏资源**。默认隔离工作分支、自动离线测试、可回滚；真实消费/实机操作必须遵守用户既有授权，发布与合并由用户或其明确授权的流程把关。
- 每个候选修复都要留下误判负例和验证边界；限时活动过期后可只保留探索材料，不强制成为正式内置功能。

## 六、建议起步顺序

1. **现有能力盘点**：先以已长跑验证的 CollectFishTask（service）及已有真实成功出口的独立 job 为样本，核对 entry、参数、业务成功/失败、中止语义，写出最小契约；不改核心 Pipeline。
2. **只读可观察性**：让外部程序能得到某个 run_id 的真实阶段、业务进展、完成/失败事件与证据入口；核验断联、手动停止、StopTask 假成功、日志静默等反例。
3. **单设备可控调度**：在不与 MFA 并发控制的前提下，由 Adapter 可靠地启动/停止一个短 job，安全恢复原 service；再试一个既有日程以外的受控时间窗口。
4. **按需添加 MaaMCP 视觉原语**：确认所用 MaaMCP 版本与 MaaFramework API 后，仅补确实缺少的识别、原子动作与异步任务控制；不预设必须 fork 或重建底层。
5. **最后做自维护闭环**：先让 Agent 输出可审查候选改动与测试证据，再逐步讨论哪些操作允许自动合并、自动部署。

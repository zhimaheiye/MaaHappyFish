# MaaHappyFish 开发与对话接手手册

**最后更新**：2026-09-24

本文记录相对稳定的协作方法、用户偏好、验证边界和历史事故。功能当前进度以 `docs/handoff/CURRENT.md` 为准；单项流程以对应 `docs/features/*.md` 为准；实时截图、日志、Git 差异和用户在当前对话中的纠正优先级最高。

## 一、文档职责与信息优先级

| 信息 | 权威来源 |
| --- | --- |
| 项目硬规则、工具边界、文件导航 | `AGENTS.md` |
| 架构、技术栈、禁止事项、非目标 | `PRODUCT.md` |
| 当前版本、完成度、MFA 实测状态、下一步 | `docs/handoff/CURRENT.md` |
| 打包发版、升级版本、推送 Tag 与发布 CI 门禁 | `docs/release-workflow.md`（唯一权威文档；调度技能：`.agents/skills/maa-release-workflow/SKILL.md`） |
| 某个功能的状态机、ROI、模板、分支 | 对应 `docs/features/*.md` |
| 游戏资源、稀缺性和实机消耗授权 | `docs/game-knowledge.md` |
| 通用返回/OCR 等 UI 约定 | `docs/ui-conventions.md` |
| 当前失败原因 | 与问题时间相符的 MFA/MaaFramework 日志、失败截图 |

发生冲突时按以下顺序判断：

1. 用户在当前对话中的明确纠正；
2. 当前真实 UI、日志和代码；
3. 功能文档与 `CURRENT.md`；
4. 较早的交接文字、旧 Agent 推断或记忆。

旧 Agent、AGY 或历史文档的结论都不是不可推翻的事实。例如用户已明确确认乐队鱼存在“跳过”按钮，任何“没有跳过按钮”的旧结论均作废。

## 二、新 Agent 接手项目的固定阅读顺序

### 第 1 层：先建立项目边界

1. 完整阅读 `AGENTS.md`；
2. 阅读 `PRODUCT.md`；
3. 阅读 `docs/handoff/CURRENT.md`；
4. 阅读本文。

完成这一层后，Agent 应能明确回答：项目支持什么环境、哪些操作禁止、当前哪些功能只是代码完成而非实机通过、这次任务属于哪个功能。

### 第 2 层：按任务补齐业务上下文

1. 阅读路由表指定的 `docs/features/<feature>.md`；
2. 涉及鱼食、金币、体力、召唤等资源时阅读 `docs/game-knowledge.md`；
3. 涉及返回、关闭、模板、OCR 或 ROI 时阅读 `docs/ui-conventions.md`；
4. 若用户提供了旧交接文字，只把它当线索，并用当前代码、日志和用户纠正复核。

### 第 3 层：读取实时工程状态

1. `git status --short`：先识别用户已有修改和未跟踪资产；
2. `git diff -- <相关文件>`：确认当前实现，而不是按记忆重写；
3. 修 bug 时读取问题发生时间附近的 `client_avalonia/logs/` 与 MaaFramework 日志；日志不是最新时按用户给出的时间或现场截图定位；
4. 阅读目标 Pipeline、关联的 `agent/my_action.py`、`agent/my_reco.py`、`agent/runtime_state.py` 和已有专项测试；
5. 画清状态分支，确认每次点击前都有当前页面门禁，再开始改动。

## 三、两种视觉证据模式

开始任何需要新模板、OCR 或 ROI 的任务时，先明确本轮使用哪一种模式。

### A. 用户手动截图模式

- 用户负责截图、裁剪、命名并给出用途/ROI；必须实际使用用户提供的数据，不能忽略后重新猜坐标或另造资产。
- 用户明确说“不用审核”时，不再质疑图片内容或自行重新裁剪；按用户描述接入代码并进行代码级验证。
- 仍要检查文件存在、JSON 可加载、正则合法、Action/Reco 引用完整，并保证不会因空参数、缺文件或未处理异常导致 Agent/客户端崩溃。
- MFA 自然流程由用户测试；文档必须把“代码级通过”和“MFA 实机通过”分开记录。

### B. 主 Agent 使用 ADB / maa-mcp 探索模式

- 主 Agent 负责逐阶段截图、OCR、点击、日志和返回状态取证；稀缺资源流程按阶段 checkpoint 推进。
- 用于 TemplateMatch 的最终裁图必须由主 Agent 同时查看完整来源画面和最终 PNG，排除游鱼、粒子、数字、倒计时、活动背景等动态内容。
- 无法判断元素是否固定、可复现时立即停止并请用户判断。
- AGY 不负责截图、裁图、ADB/maa-mcp 操作或复杂状态机实现。

### 共同硬规则

- 点击哪里、识别哪里，就从那个真实页面、尺寸和状态截图哪里。不得以“肉眼相似”为由复用其他页面、其他尺寸、展开态/收起态或选中态/未选中态模板。
- OCR/模板失败时不得跌入固定坐标点击；点击前必须验证当前页面，点击后必须验证目标状态或安全返回。
- 用户提供的说明截图只用于理解页面关系时，不能自动当作紧裁匹配模板。

## 四、用户协作偏好

1. **局部修改**：优先修正当前状态机或节点，不顺手重构无关模块，不覆盖用户已有工作。
2. **结果可核验**：结论要能对应代码、日志或测试；不能把静态测试表述成 MFA 实机通过。
3. **少问可自行确定的问题**：安全、可逆且范围明确的检查直接做；涉及付费、稀缺资源、未知业务分支或跨机器权限时停下说明。
4. **测试状态精确拆分**：成功线、重复执行/已领取线、无体力线、终止边界等分支分别登记，不能用一句“功能完成”掩盖未测分支。
5. **分支要按并列状态表达**：例如“可领取”和“已售罄”是互斥分支，不要写成线性顺序；驯鹿鱼单按钮和双按钮布局也是并列状态，不是 ROI 修正。
6. **默认只做代码级验证**：除非当前请求明确要求实机/浏览器/模拟器测试，否则运行单元测试、静态门禁、编译和差异检查，不主动做 UI 测试。
7. **廉价鱼食例外**：视觉门禁确认廉价鱼食后，可充分重复购买和投放测试；不得扩展到贝币、钻石、现实付费、其他商品或限次体力。
8. **稀缺机会优先保全**：乐队鱼体力、钓鱼次数、魔力召唤等先验证到不可逆动作前一状态，再决定是否消耗。
9. **停止必须真实停止**：长按、高频循环、滑动和轮询必须频繁检查 `tasker.stopping/running`；不能在 MFA 已停止后继续操作屏幕。
10. **不假设跨机器能力**：远程/台式机问题只能分析用户带回的日志、代码或正式产物；Agent 不能假装能操作另一台电脑。在另一台电脑 git pull 后，如果使用已有 client_avalonia 开发目录，运行 `.\tools\sync_dev_client.ps1` 同步 interface.json 和项目图标；resource 与 agent 应保持指向仓库源码目录的 Junction。
11. **Bug 直接修复**：不把“先写并运行一个失败回归”作为固定前置步骤；先读现有代码和证据，根因明确就直接最小修改，测试放在修改后用于验证和锁定契约。
12. **反馈默认局部校准**：用户否定某个具体任务、方案或表达时，只修改被否定的那一层，不自动反转此前对整个方向的工程判断；“这个任务先不做”不等于“其它可做方向也消失”。继续保留独立判断并给出仍成立的可行项。
13. **Agent 经验下沉要过确定性门槛**：`happyfishagent` 中的活动规则、坐标、截图和 Agent 手工流程可以作为探索证据与素材源，但不能机械翻译成固定坐标 Pipeline。只有目标、分支和资源边界足够稳定，且可以用当前 UI 门禁时才下沉进 Maa；临时主观目标或价值判断继续留在 Agent 层。
14. **通用能力必须留下长期文档入口**：步骤可恢复导航、全局弹窗、通用返回、统一配置和调度等跨功能能力，不能只在本轮提示词或单个功能文档中说明。实现时同步更新全局规则、受影响功能文档、`CURRENT.md`、`PROJECT_STATUS.md` 及相应审查矩阵；以后新增功能沿同一清单接入。

## 四点五、happyfishagent 作为外部探索证据源

当开发任务引用 `zhimaheiye/happyfishagent` 或本机 `D:\\happyfishagent` 时：

1. **MaaHappyFish 当前代码仍是实现事实源**：先读当前 Pipeline、Agent、功能文档与 Git diff，再用 happyfishagent 补业务事实，禁止反过来用旧 Skill 覆盖新实现。
2. **只下沉稳定语义**：把“Agent 当时怎么一步步点”提炼成页面状态、业务分支、资源边界和验证条件；Maa 继续遵循“识别当前 UI → 动作 → 验证新 UI”。
3. **素材分级使用**：小而稳定的无标注 UI 元素可裁为运行模板；整屏截图、红圈说明图和活动档案优先作为理解/离线测试 fixture，不直接作为 TemplateMatch 资产。
4. **缺安全门禁就显式阻断**：关键截图不足时记录到对应功能文档，允许状态停在 Implementation Ready / Live Blocked；不得用“没识别到付费态，所以默认免费”之类负向推断补洞。
5. **高层主观决策暂留 Agent**：如果“这次选哪个目标”“这个资源值不值得花”等仍依赖用户当次意图，不应为了自动化而强行塞进固定 Maa 任务。等规则经过多轮使用后真正泛化，再评估下沉。

## 五、AGY 的使用边界

AGY 只用于范围明确、可独立核验的辅助工作：

- 允许：按指定文件只读调查、搜索引用、运行明确列出的静态/单元/回归测试并回报原始结果；
- 禁止：截图或裁图、操作模拟器、使用稀缺资源、编写/修改代码、设计复杂状态机、替主 Agent 作最终集成判断；
- 委派时必须给出具体文件、问题、命令、禁止动作和输出格式；不得把“完成整个功能”整体交给 AGY；
- 主 Agent 仍要检查实际 Git diff，并复跑对结论关键的门禁；AGY 失败不等于项目失败，也不能无界重试。

## 六、标准开发流程

1. **确定范围**：把用户描述拆成互斥 UI 状态、动作和正常终止条件。
2. **选择证据模式**：手动截图或 ADB 探索，不能混淆两者责任。
3. **检查现状**：读文档、Git 状态、目标代码、失败日志和现有测试。
4. **设计恢复路由**：StartRouter 最深阶段优先；当前截图高于历史进度。
5. **加动作门禁**：每个点击前识别当前页面，动作后验证转换；未知状态安全停止。
6. **实现最小改动**：优先 Pipeline 表达简单分支，只有跨帧状态、高频识别或复杂计算才使用 Python Agent。
7. **修改后补验证**：根因明确时直接完成最小修改，再按需补充专项契约断言；不要求先运行一次失败测试。模板仍要做同类控件交叉负样本验证。
8. **运行门禁**：至少运行受影响专项测试、Pipeline 正则、Agent 引用完整性、Python 编译与 `git diff --check`；修改界面或发布依赖时追加相应门禁。
9. **更新文档并闭环待办**：同步功能文档、`CURRENT.md` 与 `PROJECT_STATUS.md`；涉及 Bug 时同时维护 `ISSUES.md`。跨功能通用能力还必须更新对应全局规则与审查矩阵，让后续新功能直接复用。已完成的 Bug 从待修复/进行中列表中删除或迁入已完成记录，只保留尚未满足的具体子项，并明确代码级、MFA 级或待截图边界。
10. **清理并交付**：用户明确为本次 Bug 临时复制到项目目录的日志、测试报告或现场截图，在修复和代码级验证完成后按准确路径删除；随后先报告结果，再列验证范围和仍需用户实测的具体分支。未请求时不提交、不推送、不关机。

## 七、验证矩阵

### Pipeline / Agent 通用门禁

```powershell
python dev/test_pipeline_regex.py
python dev/test_agent_registration_refs.py
python dev/test_release_agent_imports.py
python -m py_compile agent/my_action.py agent/my_reco.py agent/runtime_state.py
git diff --check
```

另需按功能运行相应 `dev/test_*.py` 或 `tests/` 用例。不能因专项用例通过就声称整个仓库全绿；若基线存在无关失败，应分开报告。

### 变更类型对应追加检查

| 变更 | 追加检查 |
| --- | --- |
| Pipeline `expected` / OCR | `dev/test_pipeline_regex.py`，特别检查正则特殊字符 |
| CustomAction / CustomRecognition | 注册引用门禁、显式返回值、`parse_dict_param()` 空值测试 |
| 新第三方 import | 更新 `agent/requirements-release.txt`，用发布 embedded Python 做 import 冒烟 |
| `interface.json` | 三份文件字节一致，运行 `dev/test_update_contract.py` |
| 模板/ROI | 文件存在、真实页面正样本、相似控件负样本；ADB 模式还要主 Agent 复核最终裁图 |
| 高频/长按/循环动作 | 停止状态单测或 Mock，确保停止后不再点击/滑动 |
| 稀缺资源流程 | 先做 replay/mock/前置页面验证，MFA 结果单独登记 |
| 打包发布 (Release) | 完整执行唯一权威文档 `docs/release-workflow.md`，通过 4 项静态门禁，两阶段更新状态，推送 tag 触发 CI 并验证 8 目标构建资产 |

## 八、历史错误与解决方式

| 错误/现象 | 根因 | 已采用或必须采用的解决方式 |
| --- | --- | --- |
| 模板包含游鱼、背景或邻近控件，换一帧就失配 | 裁图没有区分固定 UI 与动态画面 | 紧裁固定本体；ADB/脚本产物由主 Agent 结合完整截图复核；用户明确免审的手动截图按其说明接入；不确定就问用户 |
| 看起来相似的按钮/缸号在另一个页面识别失败或串号 | 复用了不同页面、缩放或状态下的模板 | 点击/识别哪个状态就从该状态单独截图，并用同类控件互作负样本 |
| 金海豚入口未识别后固定点击 `(674, 468)`，误点鱼缸游鱼 | 把坐标兜底当作导航恢复 | 删除盲点；建立鱼缸 -> 游乐园 -> 图标 -> 小游戏逐层视觉门禁 |
| `expected: "0("` 使整份 Pipeline 加载失败 | Maa 把 `expected` 当 `std::regex`，括号未转义 | 优先用“刷新体力”等稳定语义；需要特殊字符时 JSON 双反斜杠转义；每次跑正则门禁 |
| Python Agent 无故退出 | `print()` 中 Emoji 在 Windows GBK 下触发编码异常 | Python 日志禁用 Emoji；UI 文案用 Pipeline `focus` 注入 |
| 发布包 Agent LinkStart 失败，而开发机正常 | 开发机有 `cv2`，发布 embedded Python 缺依赖 | 同步 `requirements-release.txt`，CI/本地用发布 Python 真实 import |
| `custom_action_param` 为字符串 `"null"` 时崩溃 | 直接 `json.loads()` 或假定字典 | 统一使用 `agent/param_utils.py::parse_dict_param()`，Action/Reco 显式返回 |
| 购买鱼食长按或乐队鱼扫描在停止后仍继续点击 | 长循环只在入口检查停止，控制器队列仍继续 | 在每次轮询、滑动、长按分段、点击前后检查停止；停止时不写入成功状态 |
| 每日免费礼包被描述成“可领取 -> 已售罄”的线性流程 | 混淆互斥 UI 分支和领取后的无关页面 | 建模为“可领取成功线”与“已售罄重复执行线”，各自正常返回 |
| 签到页优先点关闭，导致没有签到 | 误以为关闭后还有另一层签到页 | 只有一层：必须先领取；领取后若页面仍在才点 `签到_关闭`，自动关闭则直接恢复 |
| 巡检按鱼缸重新进入海星页，三次都到了同一乖海星 | 错把鱼缸与海星对象做固定映射 | 只进入一次通用海星页，按“萌/乖/亮”标签切换并验证正文；映射可变 |
| 深海鱼食明明点击成功却反复退出重进 | 负向候选被当成成功/转换条件，且没有验证弹窗 | 使用深海页面真实加号和第一格模板；点击后同时验证弹窗关闭与当前海星正文 |
| 驯鹿鱼中间“一键收取”和左侧“一键回礼”被当作一个 ROI 修正 | 没有把两种布局建成并列状态 | 分别保留单按钮与双按钮 OCR/ROI；命中哪个执行哪个，未知页面安全返回/停止 |
| 乐队鱼第 2 个好友明明在首屏却继续下滑或误邀其他好友 | 移除了指定好友名字校验，按首项/排序/坐标猜测 | OCR 精确匹配四个指定名字，点击文字中心，验证选中态和邀请按钮；禁用搜索框与首项猜测 |
| 旧交接称乐队鱼没有跳过按钮 | 只根据不完整观察下结论，且与用户事实冲突 | 以用户确认和新截图为准；旧结论作废；稀缺体力下只在模板命中后点击 |
| 金海豚只点一次贝币后游戏不启动 | 小游戏有隐藏激活阶段 | 经验星出现前持续识别并点击贝币；经验出现后停止点币并全屏识别两种尺寸经验星 |
| 钓鱼优化被误解成切换普通 ADB | 用户指的是 Maa 自带捕获方式 | 记录并比较 EmulatorExtras/Raw/Encode 等 Maa 捕获方式；当前优化先基于日志、FPS 和截图耗时，稀缺次数不盲测 |
| 海獭末位好友与推荐玩家往返后最终报错 | `LEFT` 末位耗尽进入推荐页仍按 `RIGHT` 桥接规则校验 | `RIGHT+推荐页` 只 Prev 桥接；`LEFT+推荐页` 记为正常完成；灰色右键末位好友耗尽也正常完成 |
| 长任务工具调用超时后屏幕仍被操作 | 调用超时不等于 Maa tasker 已停止 | 长任务用有界阶段测试；调用停止后核对 `tasker_stopped`、日志和进程状态，不能只看 API 返回 |
| MaaFW 候选节点识别未命中不触发自身 on_error | 误以为候选节点的 on_error 在 recognition 返回 None 时会自救 | MaaFW 核心语义：父节点的 timeout/on_error 控制对 next 候选列表的识别等待；候选节点的 timeout/on_error 仅在该节点被成功识别、正式激活后才生效。候选识别未命中仅被视作跳过，绝不会触发候选自身的 on_error。若父节点设为 `timeout: -1` 且无候选命中，将导致无限轮询死锁。父节点必须设置有限 timeout 或默认兜底 |
| 半透明/气泡图标跨鱼缸背景失配（历史事故：v0.5.5 扳手模板） | 模板（如深海深蓝背景截取的半透明扳手）在浅色/木质鱼缸中全图 RGB 差异极大（0.49 < 0.70）导致识别失败 | 裁图紧贴前景或加绿色遮罩扣除半透明背景；当前 CollectFish 已彻底弃用扳手模板，改为先识别各鱼缸主页面编号牌确认环境后再精准点击管理入口坐标 (176, 54)，从架构上根除背景色差风险 |
| CustomRecognition 带有业务副作用导致轮询期间状态虚增（历史事故：手机看广告轮数暴增） | 误以为 CustomRecognition 仅在做出最终流转决断时执行一次，在 `analyze()` 中执行 `completed_cycles += 1`；而 MaaFW 在父节点等待期间每秒高频多次评估所有候选 candidate，导致单次弹窗停留 2~3 秒期间计数虚增数十次 | 手机广告事故中的 `completed_cycles` 属于业务事件计数，不应放在 Recognition 中；对一次性业务事件的计数与副作用应由命中后的 Action 承担。Recognition 若维护 timer/cache/scheduler 等内部状态，必须保证重复评估幂等 |

## 九、文档维护要求

- 每次 Bug 修复并通过本次约定的代码级验证后，交付前必须同步清理所有相关文档待办；用户未要求实机测试时记录“本次未做实机测试”即可，不得让已完成的代码修复继续占用“待修复”状态。
- 用户明确标注为单次 Bug 取证而复制的日志/测试报告必须在任务闭环后删除，并在交付中报告；长期项目日志、正式证据资产不在未获授权时删除。
- `CURRENT.md` 只记录当前有效状态；过期占位、旧节点数和已被用户纠正的结论应立即更新，不保留为现状。
- 功能文档要列出：支持的启动状态、成功/重复/无资源/终止分支、模板与 ROI、代码级测试、MFA 已测与未测。
- 每次新事故至少在对应功能文档记录根因；具备跨功能复用价值时再补到本文。
- 新 Agent 结束工作前必须检查文档与实现是否一致，特别是“已实现”与“已实测”的措辞。
- 通用能力变更必须同时回答三个问题：本次哪些功能已接入、哪些状态故意不支持、以后新增功能如何检查接入；答案分别落到受影响功能文档、全局专题矩阵和 `AGENTS.md`/本手册，不能只写在最终回复中。
- 全仓步骤可恢复导航统一维护 `docs/features/start-navigation-audit.md`。新增独立任务、扩展 StartRouter/ResumeRouter、改变 intentional unsupported 状态时，必须同步更新该表和对应功能文档。
